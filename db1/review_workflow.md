# DB1 双人复核流程（Review Workflow）

> 适用对象：AI 填充生成的 DB1 系统条目（`source = "AI+verified"`）。
> 设计目标：用**分工互补 + 交叉检查**取代"两个人做同样的事"，并把「AI 生成物不可作 DB3 锚点」这条约束**变成机器可执行的拦截点**，而非依赖人的自觉。

---

## 一、核心原则：锚点与数据分流

先确立一个贯穿全流程的分流概念——**同一个条目有两种命运，走两条不同的通道**：

| 去向 | 含义 | 谁来把关 | AI 生成物能否进入 |
| --- | --- | --- | --- |
| **DB2（指纹数据）** | 作为训练 A 的数据样本 | 机器门 + 抽检 | ✅ 可以 |
| **DB3（锚点规则）** | 作为 B 规则库的桥接规则理论依据 | 机器门 + 双人全量 + 文献溯源 | ❌ 不可以 |

**关键机制**：AI 生成条目的所有公式，在入库时自动被打上 `anchor_eligible = false` 标记。即使 AI 把公式写对了，它也只是"数据"，不是"依据"。要把某条公式升级为锚点，必须走 §四 的独立溯源通道。

---

## 二、复核前的机器自动门（零人工成本，全量）

机器门不通过，直接退回 AI 重生成，**不进入人工复核**。顺序：

1. **JSON Schema 校验**（`db1.schema.json`）：字段齐全、类型正确、枚举合法。
2. **约定一致性检查**（`conventions.yaml`，可脚本化）：
   - `σ` 参数化：`parameters` 里高斯系统不得出现 `σ²` 当参数；
   - SDE 默认 Itô 且 `σ²` 标注为方差速率；
   - `k_B T = 1` 或已显式记录；
   - 桥接常数带 `is_bridge_constant: true` + 单位。
3. **指纹可计算性测试**：核心信息计算库端到端跑通并输出指纹；跑不通即拒。
4. **解析对照**：`fingerprint_expectation` 逐条断言，数值 vs 解析在容差内；超差即拒。

机器门通过后，条目进入人工复核。此时 `anchor_eligible` 保持 `false`。

---

## 三、双人复核：角色与检查清单

### Reviewer A —— 物理审查员（信息论/ML 背景，第一人）

**职责**：判断"物理上对不对、约定上统不统一"。

检查清单（逐项打勾）：

- [ ] **方程正确性**：控制方程与教科书/文献一致，无符号、系数、指数错误。
- [ ] **参数物理合理性**：取值范围符合物理（如扩散系数 > 0、弛豫率 > 0）。
- [ ] **边界/初值条件**：完整且与系统族匹配。
- [ ] **约定一致性**：σ/σ²、Itô/Stratonovich、无量纲化、nats——对照 `conventions.yaml` 逐条核。
- [ ] **strictness 标注恰当**：AI 常把「推导」误标为「定理」，或把「类比」误标为「推导」。
- [ ] **channel_template 选择正确**：通道模板 ID 是否匹配系统类型。

### Reviewer B —— 信息论审查员（物理背景，第二人）

**职责**：判断"信息论映射对不对、依据可不可溯源"。

检查清单：

- [ ] **通道识别正确**：物理系统 → 信息通道（X/T/Y 划分）是否符合 §2.3.4 模板。
- [ ] **指纹解析式可溯源**：`fingerprint_expectation` 里每个解析式，是否能在 `source_ref`/`analytic_invariants` 的 citation 中找到出处。
- [ ] **MI/Fisher 估计器选择正确**：高斯用解析、非高斯用 KSG、离散用 binning（对照 `conventions.yaml` 第 1 组）。
- [ ] **锚点溯源审查（核心）**：见 §四。
- [ ] **q 向量可比性**：该条目指纹是否与同族其他条目用同一套 β 网格、同一种估计器（保证跨系统可比）。

### 交叉检查设计（为什么是两人，不是一人查两遍）

- A 的盲区是「物理对但约定漂移」——B 用**信息论一致性**视角补。
- B 的盲区是「信息论对但物理不实」——A 用**物理真实性**视角补。
- 两者共同覆盖「AI 静默改约定」这个机器门抓不住的失效模式。

## 四、锚点溯源通道（拦截 AI 生成物作锚点的硬机制）

### 4.1 触发条件

当且仅当某条目的某个公式**将被用作 DB3 桥接规则的理论依据**时（例如 §2.3.3 规则库中某规则引用了该公式），触发锚点溯源流程。

### 4.2 拦截规则

| 情形 | 处理 |
| --- | --- |
| 条目 `source = "AI+verified"`，公式要作锚点 | **自动拦截**，`anchor_eligible` 恒为 `false`，不得作为锚点提交 |
| 条目 `source = "textbook"` 或 `"literature"` | 可进入锚点溯源通道，但需 Reviewer B **独立核实文献原文** |
| AI 生成的公式正确，但想升级为锚点 | 走"重溯源"：Reviewer B 到文献库查证原始出处，将该公式改为 `source = "literature"` 并附 `citation`，重新入库 |

### 4.3 锚点提交的签核矩阵

| 去向 | 机器门 | Reviewer A | Reviewer B | 文献溯源 |
| --- | --- | --- | --- | --- |
| DB2（指纹数据） | ✅ 全量 | ✅ 抽检（≥20%） | 可选 | 不要求 |
| DB3（锚点规则） | ✅ 全量 | ✅ 全量 | ✅ 全量 | ✅ 强制 |

**结论**：AI 生成物可以大量填充 DB2，但**任何一条进入 DB3 的锚点，都必须有文献溯源 + 双人签字**。这条约束因此被结构性地执行，而非依赖自觉。

---

## 五、分歧处理

1. A 与 B 任一标记 `reject` → 条目退回 AI 重生成（附具体失败点）。
2. A 与 B 意见不一致（一个 accept 一个 reject）→ 引入**第三仲裁人**（或 A/B 共同重审原始文献）。
3. 系统性失败（同族连续 ≥3 条被拒）→ **整批回炉**，并检查该族的 `channel_template` 或约定规范是否需要修订（局部修补会掩盖系统性偏差，见架构文档 §3.9）。

## 六、签核记录（每条目必填）

```yaml
review_record:
  entry_system_id: "ou_process_1d"
  machine_gate:
    schema_valid: true
    convention_check: true
    computability: true
    analytic_compare: true
  reviewer_a:
    name: "<姓名>"
    decision: "accept"          # accept / reject
    findings: "无"
    date: "2026-09-25"
  reviewer_b:
    name: "<姓名>"
    decision: "accept"
    findings: "无"
  anchor_eligible: false         # AI 生成物恒为 false
  final_destination: "DB2"       # DB2 / DB3
  final_decision: "accept"
```

## 七、与架构文档的关系

- 本流程是架构文档 §3.9「DB1 构建」中第 4 步（双人复核）的落地细化。
- 双人复核职责从「检查物理」扩展为「检查物理 + 检查约定 + 检查溯源」，对应 v11 修订的 DB1 构建流程。
- 锚点溯源通道是架构文档 §3.2.1 第 6 组约定「AI 生成物可入 DB2，不可作 DB3 锚点」的可执行实现。
